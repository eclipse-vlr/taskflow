# TaskFlow

## О проекте

Я разрабатываю TaskFlow, чтобы разобраться с фоновыми задачами на Go: приёмом HTTP-запросов, хранением состояния, выполнением работы и восстановлением после сбоя.

HTTP API сохраняет задачи в PostgreSQL, а ограниченный пул воркеров выполняет учебные задачи `sleep`. Есть ограниченные повторы, восстановление прерванных задач, ручной повтор и отмена ожидающих задач. Клиент получает UUID сразу после записи и проверяет состояние отдельным запросом.

## Что умеет

- `GET /healthz` — возвращает `200` и `{"status":"ok"}`. Проверяет HTTP-процесс без запроса к БД.
- `POST /api/v1/tasks` — проверяет данные, сохраняет задачу, возвращает `202`, задачу и заголовок `Location`.
- `GET /api/v1/tasks/{id}` — возвращает сохранённую задачу или `404`.
- `GET /api/v1/tasks?limit=20&offset=0` — возвращает страницу задач, начиная с новых.
- `POST /api/v1/tasks/{id}/retry` — повторяет окончательно неудавшуюся задачу, возвращает `202`.
- `POST /api/v1/tasks/{id}/cancel` — отменяет ожидающую задачу, возвращает `200`.
- Задачи переживают перезапуск API и PostgreSQL, если сохранён Docker volume.
- SQL ограничен таймаутами, число соединений ограничено пулом.
- Воркеры переводят задачи `pending → running → succeeded/failed`, сохраняют результат, время выполнения и счётчик попыток.
- Неудачные попытки возвращаются в `pending` с задержкой; после исчерпания лимита задача становится `failed`.
- При запуске и затем раз в секунду сервис восстанавливает задачи с истёкшим сроком выполнения.
- По сигналу остановки прекращается приём работы, прерывается `sleep`, ожидается завершение HTTP-сервера и воркеров, затем закрывается пул БД.

## Технологии

Go 1.26 или новее, `net/http`, `encoding/json`, `log/slog`, PostgreSQL 17, [pgxpool](https://pkg.go.dev/github.com/jackc/pgx/v5/pgxpool), [golang-migrate](https://github.com/golang-migrate/migrate), Docker Compose и стандартные инструменты тестирования Go.

`pgxpool` даёт прямой доступ к PostgreSQL и ограничивает соединения. Миграции запускаются отдельно: запуск API не меняет схему. SQL использует параметры, а допустимые состояния проверяются ограничениями таблицы. Внешний брокер для MVP не требуется.

## Как запустить

Нужен запущенный Docker Desktop с Linux-контейнерами. В Windows PowerShell:

```powershell
Set-Location C:\dev\taskflow
Copy-Item .env.example .env
docker compose up -d --wait postgres
docker compose run --rm migrate
docker compose up -d --build --wait api
Invoke-RestMethod http://127.0.0.1:8080/healthz
```

Копировать `.env.example` нужно при первом запуске. `taskflow_dev` — общедоступный пароль только для локальной учебной БД. API и PostgreSQL опубликованы на `127.0.0.1`. Файл `.env` исключён из Git.

Просмотр журнала и остановка:

```powershell
docker compose logs -f api
docker compose down
```

Обычный `down` сохраняет volume с задачами. `down -v` удаляет данные; для обычной остановки он не нужен. Смена `POSTGRES_PASSWORD` не меняет пароль уже созданной БД в существующем volume. В Linux/macOS команды Compose те же, для создания `.env` используется `cp .env.example .env`.

Если БД и миграции уже готовы, API можно запустить через Go:

```powershell
$env:DATABASE_URL = 'postgres://taskflow:taskflow_dev@127.0.0.1:55432/taskflow?sslmode=disable'
go run ./cmd/api
```

В Linux/macOS: `DATABASE_URL='postgres://taskflow:taskflow_dev@127.0.0.1:55432/taskflow?sslmode=disable' go run ./cmd/api`. Go-приложение читает окружение процесса, **не загружает `.env` автоматически**.

На текущем Windows-компьютере политика управления приложениями блокирует некоторые сгенерированные `.exe`. Поэтому основной проверенный способ запуска и интеграционных проверок здесь — Docker. Образ API запускает приложение от непривилегированного пользователя.

## Настройки окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | Обязательна для запуска через Go | PostgreSQL URL с именем БД; Compose передаёт адрес сервиса `postgres` |
| `TASKFLOW_HTTP_ADDR` | `127.0.0.1:8080` | Адрес приложения; внутри контейнера — `0.0.0.0:8080` |
| `TASKFLOW_DB_TIMEOUT` | `3s` | Таймаут SQL, от `1ms` до `5s` |
| `TASKFLOW_DB_MAX_CONNS` | `10` | Максимум соединений одного процесса, от 1 до 50 |
| `TASKFLOW_WORKERS` | `4` | Число одновременно выполняемых задач одного процесса, от 1 до 100 |
| `TASKFLOW_POLL_INTERVAL` | `500ms` | Пауза свободного воркера между опросами БД, от `50ms` до `10s` |
| `POSTGRES_PASSWORD` | `taskflow_dev` | Пароль локальной БД в Compose |
| `POSTGRES_PORT` | `55432` | Порт PostgreSQL на компьютере |
| `TASKFLOW_HTTP_PORT` | `8080` | Порт API на компьютере |

Последние три переменные использует Compose. Для его локального шаблона выбирайте пароль из букв и цифр: он вставляется в URL. В отдельном `DATABASE_URL` специальные символы пароля нужно кодировать как компоненты URL. `sslmode=disable` в примерах предназначен для локальной среды.

Для другого порта API задайте `TASKFLOW_HTTP_PORT` в `.env`. При запуске через Go используется `TASKFLOW_HTTP_ADDR`. При смене порта БД исправьте также `DATABASE_URL` для запуска через Go. Старая настройка `TASKFLOW_TASK_CAPACITY` больше не используется приложением: хранилище в памяти осталось для unit-тестов.

Таймауты HTTP: заголовки — 5 секунд, чтение и запись — по 10 секунд, простой — 60 секунд, завершение HTTP-сервера — 5 секунд. Для SQL заданы также серверные `statement_timeout` и `lock_timeout`; отмена контекста отправляет PostgreSQL запрос отмены. Завершение воркеров ожидается до закрытия БД; запись их последнего состояния получает отдельный ограниченный контекст. Compose даёт процессу до 15 секунд на остановку. При недоступной БД или отсутствии таблицы `tasks` запуск завершается с ошибкой.

## Миграции

```powershell
docker compose run --rm migrate
docker compose run --rm migrate version
```

Первая команда применяет новые миграции из `migrations/`; повторный запуск сообщает `no change`. Инструмент хранит версию в `schema_migrations` и блокирует одновременное применение миграций. Первая миграция создаёт `tasks` и индексы. DDL выполняется в транзакции: ожидание блокировки ограничено тремя секундами, выполнение SQL — десятью.

Изменения схемы оформляются новой парой `NNNNNN_description.up.sql` и `.down.sql`. Уже применённые файлы не редактируются. `down` первой миграции удаляет таблицу и данные; он предназначен для одноразовой тестовой среды. При состоянии `dirty` сначала нужно проверить фактическую схему и причину сбоя; принудительно менять версию без проверки не следует.

Вторая миграция добавляет `execution_id`, `lease_expires_at`, проверку согласованности состояния и индекс просроченных задач. Перед обновлением с третьего этапа остановите старую версию API: она не поддерживает эти поля. Затем примените миграции и запустите новую версию. Уже выполнявшиеся старые задачи получат истёкший lease и будут восстановлены при запуске. Старая версия приложения несовместима с новой схемой; откат требует остановки всех процессов и отдельного отката второй миграции.

## Примеры запросов

```powershell
$body = @{
    type = 'sleep'
    payload = @{ duration_ms = 1000 }
    max_attempts = 3
} | ConvertTo-Json -Depth 3

$task = Invoke-RestMethod -Method Post `
    -Uri http://127.0.0.1:8080/api/v1/tasks `
    -ContentType 'application/json' -Body $body

$task | ConvertTo-Json -Depth 3
Invoke-RestMethod "http://127.0.0.1:8080/api/v1/tasks/$($task.id)"
Invoke-RestMethod 'http://127.0.0.1:8080/api/v1/tasks?limit=10&offset=0'

do {
    Start-Sleep -Milliseconds 250
    $current = Invoke-RestMethod "http://127.0.0.1:8080/api/v1/tasks/$($task.id)"
} while ($current.status -in @('pending', 'running'))
$current | ConvertTo-Json -Depth 3
```

Пример формы ответа создания; UUID и время будут другими:

```json
{
  "id": "c24f21f8-7af7-4136-98cc-6cd1e49bb4b2",
  "type": "sleep",
  "payload": { "duration_ms": 1000 },
  "status": "pending",
  "attempts": 0,
  "max_attempts": 3,
  "created_at": "2026-10-23T09:00:00Z",
  "updated_at": "2026-10-23T09:00:00Z"
}
```

Допустим только `sleep`. `duration_ms` — целое число от 1 до 60000. Воркер ждёт указанное время и сохраняет `result: {"duration_ms":1000}`. Ответ завершённой задачи также содержит `started_at`, `finished_at` и `attempts: 1`. При ошибке появляется `last_error`, а затем назначается повтор либо сохраняется окончательный `failed`.

`max_attempts` — от 1 до 10, по умолчанию 3; `null` тоже означает значение по умолчанию. Это общее число попыток, включая первую. После неудачи задержка составляет 1, 2, 4, 8, 16, затем 30 секунд; значение `next_run_at` видно в ответе. Задача может начаться позже этого времени, если все воркеры заняты. `last_error` сохраняется до следующего результата, текст ограничен 1024 байтами UTF-8.

Команды отмены и повтора принимают пустое тело без query-параметров:

```powershell
# Только для задачи в pending; running отменить этой командой нельзя.
Invoke-RestMethod -Method Post "http://127.0.0.1:8080/api/v1/tasks/$($task.id)/cancel"

# Только для failed; используйте ID окончательно неудавшейся задачи.
$failedTaskId = 'UUID-неудавшейся-задачи'
Invoke-RestMethod -Method Post "http://127.0.0.1:8080/api/v1/tasks/$failedTaskId/retry"
```

Ручной повтор сохраняет ID, тип, payload и `max_attempts`, сбрасывает `attempts` в 0, очищает прежние время выполнения, результат, ошибку и задержку. Отменённые и успешно выполненные задачи повторять нельзя. Несовместимое состояние даёт `409`; неизвестный или некорректный UUID — `404`. Если воркер успел захватить задачу раньше отмены, отмена вернёт `409`.

Тело `POST /api/v1/tasks` ограничено 16 КиБ и должно содержать один JSON-объект в UTF-8. Неизвестные поля, дубликаты, лишние JSON-значения и сжатие отклоняются. Имена полей сопоставляются без учёта регистра, как в стандартном декодере Go; дубликаты с разным регистром тоже запрещены.

Ответ списка: `{"tasks":[...],"limit":10,"offset":0}`. По умолчанию `limit=20`, `offset=0`; допустимы `limit` от 1 до 100 и `offset` от 0 до 1000000. Пустая страница содержит `"tasks":[]`. Неизвестные и повторяющиеся параметры отклоняются.

Порядок: `created_at DESC, id DESC`. UUID разрешает совпадения времени. Это offset-пагинация: новые задачи между запросами могут сдвинуть страницы; снимок данных на несколько запросов не гарантируется.

| Код | Причина |
| --- | --- |
| `400` | Неверный JSON, параметры задачи или пагинации |
| `404` | Задача или маршрут не найдены; неверный UUID тоже считается неизвестной задачей |
| `405` | Неподдерживаемый метод известного маршрута |
| `409` | Текущее состояние не допускает повтор или отмену |
| `408` / `504` | Контекст отменён / истёк таймаут SQL |
| `413` | Тело больше 16 КиБ |
| `415` | Требуется `application/json` в UTF-8 без сжатия |
| `500` | Внутренний сбой, например потеря доступа к PostgreSQL |

Ошибки обработчиков имеют вид `{"error":"..."}`, без параметров подключения и текста SQL. Неизвестные маршруты и неподдерживаемые методы обрабатывает стандартный маршрутизатор Go и возвращает текст. `/healthz` может оставаться успешным при потере связи с БД после запуска; это не проверка готовности PostgreSQL.

## Тестирование

Быстрые тесты без БД:

```powershell
go test ./...
go vet ./...
```

Unit-тесты проверяют HTTP-контракт, JSON и пагинацию, конфигурацию, контекст и параллельный доступ к хранилищу в памяти. Тесты воркеров с `testing/synctest` проверяют виртуальное время `sleep`, ограничение параллелизма, отсутствие захвата работы сверх свободных мест, отмену и ошибки записи результата.

Полная проверка в Docker, включая `-race`, интеграционные тесты, `go vet` и контроль модулей:

```powershell
docker compose run --rm --build test
```

Тестовый образ содержит C-компилятор для `-race`. Интеграционные тесты создают случайную схему на каждый тест и удаляют только её. Основная таблица приложения не очищается; для проверок всё равно рекомендуется одноразовая локальная БД.

Запуск через Go в среде, где разрешены сгенерированные программы:

```powershell
$env:TEST_DATABASE_URL = 'postgres://taskflow:taskflow_dev@127.0.0.1:55432/taskflow?sslmode=disable'
go test -tags=integration -count=1 ./...
```

Для `-race` нужны `CGO_ENABLED=1` и C-компилятор. С `-tags=integration` отсутствие `TEST_DATABASE_URL` считается ошибкой, а не успешным пропуском.

Проверяются запись и чтение через новое соединение, список при совпадающем времени, ограничения таблицы, `down/up` на изолированной схеме и отмена заблокированного SQL. Последняя проверка смотрит `pg_stat_activity`, пока блокировка ещё удерживается: одного возврата ошибки клиенту недостаточно.

Проверяются конкурентные захваты через несколько соединений с удержанием блокировки одной строки, недопустимое повторное завершение и полный путь `pending → running → succeeded/failed`. Тесты четвёртого этапа покрывают задержки повторов, исчерпание попыток, восстановление с новым пулом соединений, сохранение активного lease, отказ старому токену после ручного повтора, гонку отмены с захватом и одновременные ручные повторы.

На третьем этапе на живом API проверены шесть задач `sleep` при лимите двух воркеров: одновременно наблюдалось не больше двух `running`, ответы создания приходили до окончания выполнения, все результаты сохранились. В четвёртом этапе остановка прерванной задачи назначает повтор, если бюджет попыток ещё не исчерпан; тест проверяет запись состояния до закрытия пула БД.

Для четвёртого этапа на живом API проверены отмена ожидающей задачи (`200`), конфликты повторных команд (`409`), неверный UUID (`404`), штатная остановка с кодом `0`, сохранение исчерпанной попытки в `failed`, ручной повтор (`202`) и успешное повторное выполнение. После `SIGKILL` и перезапуска активный lease сохранился; через 96,5 секунды после аварии задача с пятисекундным `sleep` успешно завершилась второй попыткой. Исходное 90-секундное ожидание не сокращалось вручную. Это локальные функциональные проверки, а не нагрузочные замеры.

При проверке второго этапа миграция применилась на пустой базе, повторный запуск вернул `no change`. Созданная через HTTP задача сохранилась после перезапусков API и PostgreSQL. При остановленной БД API вернул `504` без параметров подключения; после её запуска чтение восстановилось. Сборка под Windows также прошла.

Workflow `.github/workflows/ci.yml` запускает форматирование, unit-тесты, интеграционные тесты с PostgreSQL 17 и `-race`, `go vet` и `go mod verify` на Go 1.26 и 1.27. На Go 1.27 также запускается `govulncheck` для проверки известных уязвимостей зависимостей. Actions закреплены SHA, токен имеет только право чтения содержимого. Workflow проверен локально через `actionlint`. Проверка GitHub CI требует публикации ветки; локальные тесты не подтверждают статус удалённого workflow.

## Как устроен проект

```text
cmd/api/                       запуск и остановка HTTP/БД
internal/config/               окружение и проверка настроек
internal/handler/              маршруты, JSON и HTTP-коды
internal/task/                 модель, бизнес-правила и Repository
internal/repository/postgres/  SQL, пул соединений и таймауты
internal/repository/memory/    хранилище для быстрых тестов
internal/scheduler/            опрос и атомарный захват готовой задачи
internal/worker/               фиксированный пул и обработчик sleep
migrations/                    SQL-миграции up/down
tests/integration/             реальный PostgreSQL
```

Запрос проходит через `handler → task.Service → Repository`. Сервис проверяет параметры, задаёт `pending` и создаёт UUID. Репозиторий PostgreSQL сохраняет данные; `202` выдаётся после записи. При потере соединения во время записи её результат может быть неизвестен клиенту; защиты от повторного создания через `Idempotency-Key` пока нет.

Каждый свободный воркер вызывает планировщик. Тот одним SQL-запросом выбирает готовую задачу с `FOR UPDATE SKIP LOCKED`, переводит её в `running`, увеличивает `attempts` и выдаёт уникальный токен выполнения с lease на 90 секунд. Обработчик получает контекст с пределом 65 секунд; сам `sleep` ограничен 60 секундами. Результат принимается только для текущего токена, номера попытки и ещё действующего lease. После ручного сброса счётчика старый токен всё равно не сможет завершить новую попытку.

Сервис проверяет истёкшие lease при запуске и раз в секунду. За один запрос восстанавливается до 100 задач; заблокированные строки пропускаются через `FOR UPDATE SKIP LOCKED` и проверяются при следующих опросах. Большая очередь восстанавливается несколькими партиями. Просроченная `running` возвращается в `pending`, если остались попытки, иначе становится `failed`. Активные lease не сбрасываются даже при запуске второго экземпляра. Также завершаются оставшиеся `pending` с исчерпанным бюджетом. После аварии выполнение может повториться: токен защищает запись результата в БД, но не отменяет уже совершённые внешние действия.

Очередь ожидающих задач находится в PostgreSQL. Отдельной очереди задач в канале нет: задача захватывается только свободным воркером. Число выполняемых обработчиков ограничено `TASKFLOW_WORKERS`; при нескольких экземплярах приложения лимит действует на каждый процесс отдельно. Пустая очередь и ошибки захвата приводят к паузе до следующего опроса, без создания новых горутин.

## Ограничения и планы

- Пока процесс выключен, задачи не исполняются. После аварии восстановление может ждать до 90 секунд до истечения lease, затем ближайшего опроса БД.
- При штатной остановке HTTP-сервер прекращает приём, контекст воркеров отменяется, прерванный `sleep` сохраняется с `last_error: "context canceled"`: `pending` при оставшихся попытках или `failed` при исчерпанном лимите. Запущенная попытка расходует бюджет даже при остановке процесса.
- API отменяет только `pending`. Нет отмены `running`, webhook, heartbeat-продления lease и гарантии однократного выполнения. Для новых обработчиков длиннее 60 секунд потребуется другой механизм lease и ограничения времени.
- Ошибка сохранения результата останавливает пул и приложение с ненулевым кодом. Это предотвращает приём новой работы после неопределённого результата записи. Автоматического перезапуска процесса Compose пока не задаёт.
- Нет авторизации и очистки старых задач. Compose предназначен для локального обучения.
- Миграции нужно применять отдельно до запуска новой версии API.
- Теги контейнеров могут получать обновления; образы не закреплены digest-ами.
- Workflow CI добавлен; его удалённый результат появится после публикации ветки.

Дальнейшие улучшения: `Idempotency-Key`, метрики, очистка старых задач и обработчики с идемпотентными внешними действиями. PostgreSQL остаётся источником состояния.
