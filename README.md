# TaskFlow

Я разрабатываю TaskFlow, чтобы разобраться с фоновыми задачами на Go: от приёма HTTP-запроса до выполнения работы, сохранения результата и восстановления после сбоя.

## О проекте

Планируемый сценарий: клиент отправляет задачу, получает идентификатор и проверяет её состояние отдельным запросом. Воркеры выполняют задачи независимо от HTTP-запросов.

Сейчас реализован **первый этап — каркас и HTTP API**. Сервер принимает учебные задачи `sleep` и хранит их в памяти. Выполнение появится на третьем этапе после подключения PostgreSQL.

## Что умеет

- `GET /healthz` — возвращает `200` и `{"status":"ok"}`.
- `POST /api/v1/tasks` — проверяет данные, сохраняет задачу и возвращает `202`, UUID v4 и заголовок `Location`.
- `GET /api/v1/tasks/{id}` — возвращает задачу или `404`.
- Обслуживает параллельные запросы; доступ к хранилищу защищён мьютексом.
- Ограничивает размер тела запроса и количество сохранённых задач.
- Завершает HTTP-сервер по Ctrl+C с ожиданием активных запросов до пяти секунд.

Созданная задача остаётся в состоянии `pending`, `attempts` равно `0`. `max_attempts` пока только сохраняется. **После перезапуска все задачи исчезают.**

## Технологии

Нужен Go 1.26 или новее. Внешних Go-зависимостей на первом этапе нет.

- `net/http` — маршрутизация и HTTP-сервер без отдельного фреймворка.
- `encoding/json` — обмен данными.
- `crypto/rand` — случайные идентификаторы задач.
- `sync.RWMutex` — защита хранилища при параллельном доступе.
- `log/slog` — журнал запуска, остановки и внутренних ошибок.
- `testing`, `httptest` — проверки HTTP-контракта и хранилища.

PostgreSQL, pgx и Docker Compose запланированы на второй этап.

## Как запустить

В Windows PowerShell:

```powershell
Set-Location C:\dev\taskflow
go run ./cmd/api
```

В другом окне PowerShell:

```powershell
Invoke-RestMethod http://127.0.0.1:8080/healthz
```

Остановить сервер можно сочетанием Ctrl+C в первом окне.

На компьютере, где выполнялась проверка, сборка под Windows прошла, но запуск полученного `.exe` заблокировала политика управления приложениями. Проверка живого API выполнена в Docker Desktop. Если встречается такая же блокировка, можно запустить приложение в Linux-контейнере:

```powershell
docker run --rm --name taskflow-local `
    --mount "type=bind,source=$($PWD.Path),target=/src,readonly" `
    -w /src -p 127.0.0.1:8080:8080 `
    -e TASKFLOW_HTTP_ADDR=0.0.0.0:8080 `
    golang@sha256:5cf287a799e6b94384bad13d16b14904c531f51ba65792237e122ce42b392f61 `
    sh -c 'go build -o /tmp/taskflow ./cmd/api && exec /tmp/taskflow'
```

Здесь закреплён использованный при проверке образ Go 1.27.2. Если его ещё нет локально, Docker скачает его. Для остановки из другого окна: `docker stop taskflow-local`.

При запуске собранного приложения:

```powershell
New-Item -ItemType Directory -Force bin | Out-Null
go build -o bin/taskflow.exe ./cmd/api
.\bin\taskflow.exe
```

В Linux/macOS из каталога проекта используются те же команды `go run ./cmd/api` и `go test ./...`. Исполняемый файл можно собрать командой `go build -o bin/taskflow ./cmd/api`.

## Настройки окружения

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `TASKFLOW_HTTP_ADDR` | `127.0.0.1:8080` | Адрес HTTP-сервера, порт от 1 до 65535 |
| `TASKFLOW_TASK_CAPACITY` | `1000` | Максимальное число задач в памяти, от 1 до 100000 |

Пример для PowerShell:

```powershell
$env:TASKFLOW_HTTP_ADDR = '127.0.0.1:8081'
$env:TASKFLOW_TASK_CAPACITY = '100'
go run ./cmd/api
```

Чтобы вернуться к значениям по умолчанию:

```powershell
Remove-Item Env:TASKFLOW_HTTP_ADDR -ErrorAction SilentlyContinue
Remove-Item Env:TASKFLOW_TASK_CAPACITY -ErrorAction SilentlyContinue
```

В Linux/macOS: `TASKFLOW_HTTP_ADDR=127.0.0.1:8081 TASKFLOW_TASK_CAPACITY=100 go run ./cmd/api`.

Файл `.env.example` служит справочником. Приложение **не читает `.env` автоматически**. Настройки передаются через окружение процесса; некорректные значения останавливают запуск с ошибкой.

Таймаут чтения заголовков — 5 секунд, чтения запроса и записи ответа — по 10 секунд, простоя соединения — 60 секунд. Заголовки ограничены настройкой `MaxHeaderBytes` в 16 КиБ; тело POST — строго 16 КиБ. Формат и таймауты подходят текущим коротким запросам без потоковой передачи.

## Примеры запросов

Создать задачу в PowerShell:

```powershell
$body = @{
    type = 'sleep'
    payload = @{ duration_ms = 1000 }
    max_attempts = 3
} | ConvertTo-Json -Depth 3

$task = Invoke-RestMethod -Method Post `
    -Uri http://127.0.0.1:8080/api/v1/tasks `
    -ContentType 'application/json' `
    -Body $body

$task | ConvertTo-Json -Depth 3
Invoke-RestMethod "http://127.0.0.1:8080/api/v1/tasks/$($task.id)"
```

Пример формы ответа; идентификатор и время при запуске будут другими:

```json
{
  "id": "c24f21f8-7af7-4136-98cc-6cd1e49bb4b2",
  "type": "sleep",
  "payload": { "duration_ms": 1000 },
  "status": "pending",
  "attempts": 0,
  "max_attempts": 3,
  "created_at": "2026-10-22T09:00:00Z",
  "updated_at": "2026-10-22T09:00:00Z"
}
```

Допустим только тип `sleep`. `payload.duration_ms` — целое число от 1 до 60000. Необязательный `max_attempts` — целое число от 1 до 10, по умолчанию `3`; JSON `null` для этого поля также означает значение по умолчанию.

Тело должно содержать один JSON-объект в UTF-8. Неизвестные поля, повторяющиеся имена полей, дополнительные JSON-значения и сжатое тело отклоняются. Имена полей сопоставляются без учёта регистра, как в стандартном декодере Go; дубликаты с разным регистром тоже запрещены.

Пример ошибки в PowerShell (сервер вернёт `400`):

```powershell
try {
    Invoke-RestMethod -Method Post `
        -Uri http://127.0.0.1:8080/api/v1/tasks `
        -ContentType 'application/json' `
        -Body '{"type":"sleep","payload":{"duration_ms":0}}'
} catch {
    [int]$_.Exception.Response.StatusCode
    $_.ErrorDetails.Message
}
```

| Код | Причина |
| --- | --- |
| `400` | Некорректный JSON или параметры задачи |
| `404` | Задача или маршрут не найдены |
| `405` | Неподдерживаемый метод известного маршрута |
| `408` / `504` | Контекст операции отменён / истёк срок операции |
| `413` | Тело больше 16 КиБ |
| `415` | Требуется `application/json` в UTF-8 без сжатия |
| `503` | Хранилище заполнено |
| `500` | Внутренняя ошибка; подробности остаются в журнале сервера |

Ошибки обработчиков возвращаются как `{"error":"..."}`. Неизвестные маршруты и неподдерживаемые методы обрабатывает стандартный маршрутизатор Go, который возвращает текст.

## Тестирование

Из корня проекта:

```powershell
go test ./...
go vet ./...
go test -race ./...
```

Для `-race` в Windows необходимы `CGO_ENABLED=1` и совместимый C-компилятор. Если их нет, обычные тесты доступны, а проверку гонок можно выполнить в Linux с C-компилятором, например в официальном образе Go через Docker Desktop:

```powershell
docker run --rm --mount "type=bind,source=$($PWD.Path),target=/src,readonly" `
    -w /src -e CGO_ENABLED=1 `
    golang@sha256:5cf287a799e6b94384bad13d16b14904c531f51ba65792237e122ce42b392f61 `
    go test -race ./...
```

При отсутствии образа Docker скачает его. Docker не нужен для обычного запуска первого этапа.

Тесты проверяют создание и чтение задач, границы параметров, ошибки без сохранения задачи, ограничение тела и ёмкости, сокрытие внутренних ошибок, отмену контекста и параллельные обращения к хранилищу. Реальная БД и выполнение задач на этом этапе отсутствуют.

На первом этапе проверены: `go test ./...`, `go vet ./...`, сборка Windows-приложения, `go test -race ./...` в Linux-контейнере. На живом сервере проверены healthz, создание и чтение, ответ `400` для неверных параметров, `404` для неизвестной задачи и `503` при заполнении хранилища. Остановка по SIGTERM в контейнере завершилась с кодом `0` и записью `HTTP server stopped` в журнале.

## Как устроен проект

```text
cmd/api/                      сборка приложения, HTTP-сервер и его остановка
internal/config/              переменные окружения и проверка настроек
internal/handler/             маршруты, JSON и HTTP-коды
internal/task/                модель, состояния, правила создания и Repository
internal/repository/memory/   временное хранилище в памяти
```

Запрос проходит через `handler → task.Service → Repository`. Сервис задаёт начальное состояние, проверяет параметры и создаёт идентификатор. HTTP-обработчик отвечает за формат запроса и ответа. Интерфейс репозитория принадлежит пакету задач; на втором этапе его реализует PostgreSQL-хранилище.

## Ограничения и планы

- Список задач, повтор и отмена пока не реализованы.
- Задачи не выполняются, результаты отсутствуют. Объявленные состояния кроме `pending` пока не используются.
- Хранилище общее только внутри одного процесса. Задачи занимают место до его перезапуска; удаления и очистки пока нет.
- Нет авторизации. По умолчанию сервер слушает локальный адрес; текущий API предназначен для локального обучения.
- В проекте пока нет Dockerfile, миграций и GitHub Actions.

Дальнейшие этапы: PostgreSQL и миграции; ограниченный пул воркеров и `sleep`; затем повторные попытки, восстановление после сбоя, отмена, завершение воркеров и CI. PostgreSQL будет источником состояния задач. Для MVP внешний брокер не требуется; обещания однократного выполнения нет.
